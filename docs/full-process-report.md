### 最初哪些判断不能直接成立

摄像头掉线仅是一项同时发生的异常，现有本案材料没有证明它被同一恶意程序感染或发生局域网横向传播。面板中 Docker 消失也不能单凭界面认定已被完整卸载，套件文件损坏、服务故障等都可能造成页面异常。

相同后缀和勒索信只能用于初步分类。要判断工具是否适用，还需样本摘要、代码布局、运行模式、密文尾记录和实际副本验证。本案样本记录的 SHA-256 与已审阅参考样本相同：

## 03 隔离与保全的处置顺序

### 先阻断扩散并保留管理通道

本案采用一台救援 Mac 与 NAS 单根网线直连，NAS 其他网口及原家庭网络连接断开。初期救援 Mac 关闭 Wi-Fi，另一台设备负责查资料和沟通。10 月 31 日用户提出改由救援 Mac 的 Wi-Fi 接手机热点、网线继续直连 NAS；助手同意只有在逐项核验路由、互联网共享、桥接和转发之后才采用。资料截点前尚无这些当前配置的实测结果，因此这里记录为**拟议方案，未证明已经启用或验收通过**。[S01、S04]

新发生事件时，可以按下列顺序处理。若无法及时阻止正在持续的数据破坏，应立即寻求现场响应支持，不应为了无限期等待完美采集而放任加密继续。

1. 记录发现时间、屏幕异常、设备状态和已经做过的改动，隔离 NAS 与其他设备的网络通道。
2. 保留可信管理通道，在已确认身份的加密进程上停止继续加密，并复核全部线程状态。
3. 尽快采集可取得的易失证据、样本及身份信息，保存原件、独立副本和摘要收据。
4. 在干净分析机检查密文副本和恢复条件，先做单文件验证，再决定批量范围。
5. 完成数据验收和证据保全后，安排系统调查、可信重建和凭据更换。

内存保全前不应把重启、升级 DSM、重装套件、清理样本或强制终止进程作为第一步。与数据恢复无关的大规模扫描和复制也不应占用最早的采集窗口。已经关机的设备仍应保留磁盘、备份和日志，寻找其他恢复路径，不要为了“找回 RAM”反复开关机。

### 救援电脑的网络检查

本案关闭互联网共享、文件共享及不需要的远程服务，不把 NAS 共享目录挂载到 Mac，不运行从 NAS 取得的程序。Mac 自身的入站防火墙与 IP 转发属于不同层面，不能用“防火墙开着”代替转发检查。

在 Mac 本地执行以下只读检查：

```sh
/usr/sbin/networksetup -listallhardwareports
/sbin/ifconfig bridge0
/usr/sbin/sysctl net.inet.ip.forwarding net.inet6.ip6.forwarding
/sbin/route -n get 169.254.100.2
/sbin/route -n get default
```

若采用救援 Mac 同时连接热点和 NAS 的拟议方案，目标状态应为 NAS 地址走 `en7`、默认路由走 Wi-Fi，两个转发值均为 `0`，`bridge0` 不包含 `en7`，系统设置中的互联网共享为关闭。应在救援 Mac 本地读取并记录实际结果；历史上一次接口排查曾发现不同接口的链路本地路由冲突，不能用旧结果代替本次复核。接口名称要通过硬件端口列表确认；`bridge0` 存在本身不代表发生桥接。

### 跨电脑交接及临时联网方案

用户询问如何把本窗口的沟通带到另一台救援电脑。讨论过使用 Codex 的只读分享快照，但它可能包含现场截图、图片和路径；个人分享链接可由持有链接者访问。为控制传递内容，随后整理了不含密钥字节、原始内存和业务文件的《救援电脑交接摘要.md》，计划用干净 U 盘带到救援 Mac，再由该机上的 Codex 先阅读摘要并只做只读状态核验。生成摘要及其文件校验已完成；对话没有确认它已经复制到 U 盘或在救援 Mac 上被读取。

用户最初询问能否让救援 Mac 用 Wi-Fi 接手机热点、网线继续直连 NAS 并使用 Codex；首次建议仍由另一台 Mac 联网，救援 Mac 保持离线。用户说明已暂停已知病毒进程，并提出关闭“互联网共享”、桥接或 IP 转发后再使用。随后将建议调整为有条件可行，但要求先核验：

1. 在救援 Mac 系统设置确认互联网共享关闭，检查桥接成员中不含直连网口；不要因为 `bridge0` 存在就删除它。
2. 用 `sysctl net.inet.ip.forwarding net.inet6.ip6.forwarding` 核对 IPv4 和 IPv6 转发均为 `0`。
3. 连接热点后再查路由，确认 `169.254.100.2` 仍经 `en7`，默认路由经 Wi-Fi；再次检查转发值。
4. 不启用代理软件的局域网监听、SSH 隧道或端口转发；Codex 只应运行本机受控脚本并回报状态，不把密钥或内存内容输出到对话上下文。

这是一项有条件的操作建议，不是救援 Mac 当前配置的验收报告。用户说已暂停的是 PID 23393 的 `libgld`，这不能证明 NAS 上没有其他恶意活动。资料截点时没有现场回报互联网共享、桥接成员、转发值或双路由检查结果，故不记录为已联网或 NAS 与互联网已可靠隔离。交接时应让 Codex 先执行只读核验，再决定是否继续；保持 NAS 供电、目标进程暂停和现有证据保全。[S01、S04]

## 04 Mac 直连 NAS 的网络排障

### 从旧地址改为链路本地直连

最初尝试沿用 NAS 原私网地址。用户确认救援 Mac 已将 USB 以太网设为 `192.168.50.250/24`，网线由 NAS 网口直接连接 Mac 网口；对 `192.168.50.5` 连续 ping 四次均超时，SSH 随后返回 `no route to host`。照片显示 Mac 的 `en7` 为 `192.168.50.250/24`、千兆链路 active，但到 `.5` 的 ARP 为 incomplete，说明尚未解析出该地址的对端 MAC，不能证明 NAS 仍使用旧地址或已经损坏。

接下来先被动抓取 `en7` 上的 ARP、DHCP 和 IPv6 报文；当时没有发现可确认的 NAS 地址。随后对 `ff02::1` 发起限定网口的 IPv6 组播探测并查看邻居表，出现的 `fe80::...%en7` 是救援 Mac 自身地址。现场使用的只读发现命令为：

```sh
sudo tcpdump -i en7 -nn -e -p -c 20 'arp or (udp and (port 67 or port 68)) or icmp6'
ping6 -n -c 3 -I en7 ff02::1
ndp -an | grep en7
```

Synology Assistant 未预装，因此沟通 Mac 从官方来源取得 7.0.7-50095 安装包（19,257,439 字节，SHA-256 为 `12c67dcf2bd77398941b51183e693fe88d9a79da212652c8a0f0a13682848b5e`），经 U 盘转到救援 Mac 后安装并搜索；搜索仍未发现设备。用户确认应用的“本地网络”权限原本已开启。于是按建议在助手搜索时另开一次 `arp or udp` 抓包：

```sh
sudo tcpdump -i en7 -nn -e -p -l 'arp or udp'
```

这次抓包照片中观察到对端 MAC `02:00:00:00:00:02` 从 `169.254.100.2` 发出报文，才把它作为 NAS 地址候选。救援 Mac 的直连接口改设为 `169.254.100.1/16`，路由器与 DNS 留空，再以 `NAS_ACCOUNT@169.254.100.2` 尝试 SSH，用户随后确认“进去了”。该地址来自本次现场观察，公开版已替换为示例，不是所有群晖的默认地址。上述搜索工具只用于发现设备，没有执行 DSM 安装、修复、迁移或重置。[S01、S02]

### 网线正常仍然连不上的原因

USB 网卡显示 1 Gbps，地址也正确，但目标连接失败。查询发现 Wi-Fi `en0` 与直连网卡 `en7` 同时存在 `169.254.0.0/16` 路由，未限定接口时，NAS 目标被选到 `en0`。因此链路灯亮、网卡有 IP 只能证明局部条件，不能证明数据包会经过正确接口。

当时 ping 与 TCP 探测曾报 `Cannot allocate memory`。对 `en7` 同期抓包，没有看到相应 ARP 或 TCP 请求，结合其他接口和 loopback 测试，问题定位在 Mac 本地发包或选路路径。该报错没有证明 NAS 内存耗尽，也不是 SSH 服务主动拒绝。

```sh
# 在 Mac 一个终端抓包，在另一个终端同时探测
sudo /usr/sbin/tcpdump -n -i en7 -e 'arp or tcp port 22'
```

抓包与探测必须覆盖同一时段。只查看过去一段没有流量的抓包，不能得出“包没有发出”的结论。

### 手工静态路由没有成为最终修复

排查中曾增加一条限定 `en7` 的目标主机路由。它改善过部分接口限定探测，但 TCP 随后仍在本机 `connectx` 阶段失败。确认该条路由是本次临时添加后，仅撤销这一条主机路由，保留系统其他路由。随后由 `en7` 的 ARP 学习路由接管，配合绑定接口和源地址，ping、TCP 22 和 SSH 均成功。

本案的最终状态是**临时静态主机路由已删除**。不要把“添加这条路由”当成通用修复，也不要在别人的机器上不看路由表就删除现有路由。

其他排除结果包括：桥接成员不含 `en7`，IPv4/IPv6 转发为零；PF 的 `No ALTQ support` 不是此次连接失败的证据；通配 anchor 查询报错也不能证明没有防火墙规则。记录中没有通过全面关闭防火墙或拆除桥接来解决问题。

### 逐层验证恢复连接

本案使用的 Mac 检查命令如下，参数需按现场替换：

```sh
/sbin/route -n get -ifscope en7 169.254.100.2
/sbin/route -n get default
/sbin/ping -n -c 1 -b en7 -S 169.254.100.1 169.254.100.2
/usr/bin/nc -vz -G 3 -b en7 -s 169.254.100.1 169.254.100.2 22
```

登录时显式绑定直连网卡和源地址，并禁止代理、X11 及端口转发：

```sh
/usr/bin/ssh -F /dev/null -a -x \
  -B en7 -b 169.254.100.1 \
  -o ClearAllForwardings=yes -o ConnectTimeout=5 \
  NAS_ACCOUNT@169.254.100.2
```

核对已有可信主机指纹。`ssh-keyscan` 可取得公钥，但它本身不能认证对端；指纹变化时先调查，不自动删除 `known_hosts` 或关闭校验。登录成功只证明通道可用，不能证明 NAS 可信。

## 05 核实加密进程并保留易失证据

### 核实 PID 与全部线程

本案进程名为 `libgld`，PID 23393，`/proc/23393/exe` 指向 `/usr/bin/libgld (deleted)`，有 5 个线程，线程号分别为 23393、23395、23396、23397、23398。后续多次记录均显示它们为 `T (stopped)`，`TracerPid` 为 `0`。[S01、S03]

`(deleted)` 表示原可执行文件的目录项已删除，运行进程仍可能保有映射和内核引用。它不能解释为“病毒已经清除”。此时 `/proc/PID/exe`、进程映射和内存仍可能提供重要证据，先结束进程会失去这条机会。

在 NAS SSH 窗口使用只读检查，其他设备必须替换 PID：

```sh
date -u
uptime
grep -E '^(Name|State|Pid|PPid|TracerPid|Threads):' /proc/23393/status
sudo readlink /proc/23393/exe
for f in /proc/23393/task/*/status; do
  grep -E '^(Pid|State|TracerPid):' "$f"
done
```

普通账号读 root 进程的链接失败，可能是权限限制。先记录退出码及报错，必要时在该终端交互执行 `sudo -v` 或 `sudo -i`，由设备所有者输入密码。临时凭据缓存不等于永久免密，也未必在另一个 SSH 会话生效。

### 暂停与终止的差别

在确认某进程正在加密且已完成 PID、启动时间和样本身份核验后，停止信号可以阻止其继续执行，同时保留地址空间。其他新事件中可由响应人员对**已核实的目标**使用 `sudo kill -STOP PID`，随后检查全部线程，不能只按名字批量操作。本案进程已经暂停，记录阶段不再发送 STOP，更不发送 CONT 或 KILL。

若信号后仍为 `D` 状态，不能宣称加密已停止；应观察全部线程、CPU 时间及 I/O 变化并继续调查。进程状态、开始时间与可执行摘要需要一起记录，避免 PID 重用导致采错对象。

## 06 物理 DSM 内存采集的过程与缺页分析

### 为什么没有照搬 PVE 整机内存方案

外部参考事件从 PVE 来宾 RAM 找到恢复材料。本案是物理裸机，没有对应的可信宿主内存接口。磁盘快照也不包含进程内存。本案改为读取已暂停进程的可读映射，经 SSH 二进制流写到 Mac；没有在 NAS 上先生成数 GiB 的 dump 文件。[S03、S09]

采集前记录 CPU 架构、内核、Python、进程启动标识、线程状态及样本摘要，并检查接收盘容量。进程映射约 6.08 GiB。采集工具与 stderr 日志分流，保存发送端字节数、流 SHA、SSH 退出状态、接收端落盘读回结果及每个映射的收据。

### v1 采集失败和 v2 的修正

用户报告救援 Mac 约有 580 GB 可用空间后，采集前检查确认 NAS Python 3.8.15、x86_64、约 6.08 GiB 可读映射，`/proc/PID/mem` 接口可打开，5 个线程处于暂停状态。此前准备的 v1 工具在沟通 Mac 通过 13 项合成测试。一次密码输入错误由用户明确说明是自己输错，之后的检查成功；这不是采集失败原因。

第一次实际采集的 v1 在第 15/19 个映射附近发生 `OverflowError`，日志记录已写出 6,529,812,480 字节、来源状态 `FAILED`、SSH 退出码为 1。失败的 `.tar.part` 及日志保留，没有重命名成完整证据或删除；v2 的重试入口先对救援 Mac 上这段失败流做来源收据读回校验，再开始独立采集。

本地测试复现了 `os.pread` 处理极高地址时的偏移溢出。v1 只捕获 `OSError`，导致该异常提前结束采集。v2 增加溢出处理、逐页重试、缺页地址及原因记录，继续采集后续区域；修正后的 v2 通过 20 项本地测试。这修复了**遇错中止和记录不足**，没有使原本不可读的页变得可读。第一次 v2 采集完成后，用户考虑到现场数据难以再现，要求再保留一份独立采集；确认启动器每次创建新目录后执行，没有覆盖旧证据。第二份 v2 的记录目录为 独立的新建采集目录（私人目录名省略）。

两份 v2 独立采集均处理了 19 个映射，来源流、接收端读回和映射文件摘要检查通过，但均为 `PARTIAL_HOLES`。它们分别封存，未将两次活系统采集拼接成一份“完整内存”。重复采集增加了独立证据副本，但没有补回相同缺页；后续因此停止继续重采，改为在救援 Mac 上离线检查副本。

### 相同的 12 KiB 缺页是什么

| 映射 | 缺失长度 | 读取结果及解释 |
|---|---:|---|
| `[vsyscall]` | 4,096 字节 | 高地址 `0xffffffffff600000`，`os.pread` 偏移无法表示，记为 `address_offset_overflow` |
| `[vvar]` | 8,192 字节 | `/proc/PID/mem` 读取返回 EIO，记为 `errno_5`；属于内核提供的特殊映射 |
| 合计 | 12,288 字节 | 采集状态仍为部分缺页，不能把零占位当作实际内容 |

最初仅有错误类别，后续通过提权只读查看映射表，才将这两处对应到 `[vsyscall]` 和 `[vvar]`。因此最终解释依据后续核验，不能假装首次失败时就已查明所有原因。

增加 sudo 权限能解决读取 maps 的权限问题，不能修复高地址表示限制，也不能保证内核允许读取特殊页。两次都缺同样位置，重复运行相同工具没有补回这些页面。

### 为什么仍然可以继续验证恢复材料

离线提取器检查候选所需的代码、模式字节、指针和 48 字节材料是否与缺页重叠；有重叠就拒绝。此次候选取自已校验且不跨已记录空洞的区域。后来真实密文与精确原件的验证表明，这些材料足以恢复已验证文件。该结果不改变“采集不完整”这个事实。

三个结论应分开：传输摘要一致说明收到的字节一致；映射摘要一致说明保存的映射与收据一致；恢复成功需要另外的文件验证。即便工具显示 `COMPLETE`，也只代表选定的可读映射没有报告空洞，不包括全部地址空间、寄存器、内核 RAM 或已释放页。

没有为追求完整而在受灾 DSM 上盲装 AVML、加载 LiME 或不匹配的内核模块。已审阅上游记录没有提供本物理 DSM 的实机验收依据；工具兼容性和现场崩溃风险必须另行评估。

## 07 从内存候选到真实文件验证

### 恢复材料的含义

离线检查对选定采集的 19 个映射完成摘要核验，并在检查样本摘要、非 PIE 的 x86-64 代码签名、运行模式与指针布局后保存 48 字节结构候选。由于救援 Mac 上有多份采集，离线入口增加了显式指定第二份归档的参数，避免自动选错；该入口在沟通 Mac 的 8 项合成测试通过。用户随后发来的现场结果显示映射摘要 `19/19` 通过且候选已保存。这些是本地测试和救援 Mac 输出两类证据，不能互相替代。候选由 16 字节 IV 与 32 字节 AES 密钥组成，不是所谓“384 位 AES 密钥”，也不是攻击者 RSA 私钥。用户询问 12,288 字节缺页是否要补时，检查确认提取器会拒绝任何与缺页重叠的候选依赖字节；候选已保存只说明这次提取所需字节未跨洞，不等于候选已通过真实文件验证。

在已分析格式中，这份材料用于解开文件尾部的 48 字节记录，取得文件级 ChaCha8 密钥及 nonce，再按对应的加密分段方式恢复文件内容。候选文件只在 Mac 私有目录保存，未打印、贴到聊天或上传 NAS。

### 第一张 JPG 为什么被严格工具拒绝

第一份测试密文比已知原图大 588 字节，符合已分析 footer 长度，但原工具预期的尾标记 `ce35a593` 不匹配，因此在检查密文结构阶段退出。**这次退出发生在检查候选密钥之前**，不能解释成密钥错误。

先比对 NAS 与 Mac 密文的字节数和 SHA-256，确认传输没有改变文件。随后复核尾记录、模式、原始长度和 key record，确认本案现场标记为 `e921db3b`。在独立测试入口中显式配置这个已核实的标记，保留其余检查，要求输出与精确原件 SHA 一致。首张 JPG 通过完整 SHA 与逐字节比较，之后第二张 JPG 也通过，再验证一张 HEIC 成功。[S01、S05]

这一步的经验是：先确定“拒绝发生在哪一层”，再根据证据修正事件参数。不能删除 footer、nonce 或长度判断来强行解密，也不能把一个四字节标记当作家族通用识别码。原严格启动器仍保留，批量流程固定解密器摘要并单独配置本案 profile。

### 实际支持的格式参数

| 字段 | 本案已核实情况 |
|---|---|
| EOF 尾记录 | 588 字节，检查记录是否确实位于文件末尾及原长度是否一致 |
| crypto mode | `0x20`；未知模式不能继续套用 |
| 文件模式 | `0x24` 全文件、`0x26` 首 1 MiB、`0x25` 分段；本案分段参数见 `10` |
| key record | 解开后检查重复 nonce；这是结构一致性检查，不是完整文件认证 |
| 输出策略 | 只读独立密文副本，只创建不存在的新文件，拒绝覆盖与不安全链接 |

有尾部追加日志、截断、重复加密、加密中断或其他运行模式时，现有解密器可能拒绝。拒绝后应单列分析，不能简单去掉检查。本案上游参考事件就存在重复加密仍未恢复的文件，说明“同样后缀”远不足以保证成功。

### 精确原件怎样选

首次安排单文件解密测试时，用户表示如有需要可以寻找照片原件；这只是愿意之后查找，并未表示当时已经找到或提供原件。早期单文件工具要求 Python 3.9+、NumPy 和 `cryptography`；沟通 Mac 当时缺少 NumPy，因此只准备离线预检和目录准备脚本，没有在沟通 Mac 上运行真实解密。`PREPARE-TEST-DIRS.command` 的 Bash 语法与工具摘要检查通过，但历史记录没有证明它已在救援 Mac 实际运行。原件应来自感染前的备份、手机或照片库未修改原片。聊天软件转发、截图、重新编码、旋转或编辑都会影响字节，不能作精确 SHA 对照。文件名不同也不代表不对应：本案 NAS 曾按拍摄日期重命名，手机原片仍保留另一名称。

一次 HEIC 对照最初按名称和近似时间找错对象，不能通过原件比较。后续在全量输出中按 SHA 搜索，找到它实际对应的是另一张恢复照片，使精确原件验证从 3 份增加到 4 份。原失败记录未删除，新增匹配另写复核报告。

没有原件时仍可做密钥记录、格式解码和应用验收，但必须按实际证据说明等级，不能把“图片打开了”写成“与历史原件逐字节一致”。

## 08 复制照片目录时遇到的问题

### SSH 可用而 SCP 默认失败

现代 OpenSSH 的 `scp` 默认使用 SFTP 子系统。本案 NAS 没有提供该子系统，报错为 `subsystem request failed on channel 0`。问题发生在传输协议层，不是密文坏了，也无需为了复制临时修改 NAS 的 SFTP 服务。

本案改用大写 `-O` 指定旧版 SCP，经已有 SSH shell 复制成功。下例仅用于一个已知、可信路径的文件，账号和路径需替换：

```sh
# 在 Mac 本地执行，目标目录需预先建立
/usr/bin/scp -O \
  -o BindAddress=169.254.100.1 \
  -o ConnectTimeout=10 \
  'NAS_ACCOUNT@169.254.100.2:/volume1/photo/EXAMPLE.jpg.L0CK3D' \
  "$HOME/NAS-rescue/copies/"
```

旧版 SCP 涉及远端 shell 路径处理，应正确引用空格等特殊字符，避免接受任意拼接命令。它也不提供可靠的中断续传，复制大目录时须预留时间并保留失败现场。

### rsync 报错停在哪一层

NAS 有 rsync，但多次尝试在 SSH 认证阶段出现 `Permission denied`，随后 `unexpected end of file`。当远端 rsync 尚未启动时，后一个报错不能解释成 rsync 协议不兼容。记录中账号大小写也有混用，后来换成曾成功的写法仍存在失败，因此没有把全部原因确定为账号大小写。

本案停止反复认证，采用已验证的 `scp -O -r` 递归复制照片目录。适用其他设备时，可先做 rsync dry-run；实际认证及兼容性通过后再选择它。无论使用哪种工具，最终仍需清单和摘要证明完整性。

### 传输显示 100% 仍不足以判定完整

Termius 后来返回 shell 提示符，末尾文件显示 100%，本机也没有活动 scp 进程。但此前执行其他命令覆盖了原 SCP 退出码，无法追溯它是否为 0。文档不补写一个成功退出状态，改由来源和副本逐路径 SHA 核对建立证据。

复制前基线与初始本地副本差异如下：

| 项目 | NAS 基线 | 初始本地副本 |
|---|---:|---:|
| 普通文件数 | 91,121 | 91,109 |
| 密文文件数 | 63,667 | 63,656 |
| 普通文件总字节 | 98,142,633,563 | 98,133,429,233 |

总数净差 12 个文件，不能直接推导为“只漏了 12 个”。逐路径检查最终解释为 13 个大小写合并、2 个权限遗漏，以及本地新增 3 个 `.DS_Store` 抵消部分差额。另有 10 条子路径因父目录大小写合并而改变拼写，内容需要按 SHA 重新对应。

### 怎样补齐而不改写原镜像

NAS 与 Mac 的大小写语义不同，只有大小写不同的路径可能在接收盘合并。仅靠文件数量、总字节数或相似文件名不能识别双方内容。后续流程按相对路径、类型、尺寸及 SHA 建立 JSONL 清单，并处理 Unicode 规范化、大小写冲突和父目录冲突。

普通账号完整扫描取得 91,119 份摘要，仅两个文件权限不足；通过一次管理员提权只读补采补齐。没有为了两个文件重跑或覆盖全部扫描。最终另存 38 份独立补充副本，合计 17,010,541 字节，覆盖冲突双方、路径错配和权限缺失。

以 91,083 份原镜像文件加 38 份补充副本，逐路径对应全部 91,121 个普通文件；额外的 27 个符号链接只记录链接及目标，没有在 Mac 自动重建可跟随链接。恢复输出通过带唯一后缀的路径映射保留大小写两侧，不能随意覆盖一个版本。

另一个清单问题是 NAS `stat -c` 把 `\t` 当作普通字符，导致第一次格式比较无效。先修正序列化，再比较路径；对可能包含特殊字符的文件名，优先使用 JSONL 等明确编码，不用按空格拆字段。[S05]

## 09 照片批量恢复与完整性验收

### 进入批量流程前的条件

照片目录约 92 GiB，最初 Mac 可用约 498 GiB，能够容纳密文副本、恢复输出及必要工作空间。工具先确认来源清单完整、本地输入 SHA 一致、候选唯一且长度为 48 字节、解密器源码摘要固定、输出路径无冲突、容量足够。

七个代表样本先覆盖三种模式、已知原件、大视频、PNG 和 CR3，再对全部已验证密文副本恢复。逐文件保存输入来源、SHA、原始路径、输出映射、模式、恢复大小、结果及验证等级。恢复失败、来源变化或记录不匹配时单列停止，不静默跳过。

### 最终恢复量与字节数核对

| 输出分类 | 文件数 | 输出字节数 |
|---|---:|---:|
| 主照片和视频 | 9,423 | 78,921,234,906 |
| Synology 缩略图与索引等元数据 | 54,243 | 19,143,664,789 |
| 附属文件 | 1 | 6,148 |
| 合计 | 63,667 | 98,064,905,843 |

本批解密任务失败为 0。输入密文总长 98,102,342,039 字节，输出总长恰等于它减去 `63,667 × 588` 字节尾记录。该算式帮助发现截断或数量问题，仍不能单独证明明文正确。

独立重开全部输出，重新计算 SHA，与恢复日志逐项一致；实际输出集合与清单也一致。输入的身份、尺寸和时间检查未发现变化。后续遗漏复核再次检查 63,667 份输出，缺失和重复均为 0。

未进入解密输出的非加密源文件为 17,836 份赎金说明与 9,618 份零字节元数据，均在证据中保留。它们与密文数量相加正好对应普通文件基线；未发现遗漏的非空未加密照片。27 个符号链接指向的视频也都有对应恢复结果。[S05、S06]

### 验收记录如何理解

首次批量报告中的“3 份精确原件”被后续复核更新为 4 份；首次仅查容器的媒体又在实况阶段补充解码。后续记录补充了结论，不删除原来的阶段性日志。

全量输出 SHA 读回一致，只能证明输出保存稳定且与本次记录一致。要证明文件等于感染前原件，需要独立历史 SHA 或精确原件。本案只有 4 份具备这种最强证据；其余按图像解码、视频轨解码、容器结构或仅密钥记录分别说明。

照片内容恢复没有同时还原所有 NAS ACL、扩展属性、原时间戳、空目录、硬链接拓扑和可跟随符号链接，因此不是可直接覆盖 DSM 的完整文件系统镜像。

## 10 实况照片配对与媒体深度核验

### 为什么不能只按同名 HEIC 与 MOV 配对

iPhone 实况照片通常包含静态 HEIC/JPEG 和一段 MOV。同步工具可能重命名其中一方，重名也可能碰巧对应不同资产。本案先前按文件名看似对应的 5 组资源，内部标识实际不同；必须按文件内的实况资产标识重新关联。[S07]

处理流程读取照片与 MOV 的内部 content identifier，检查 MOV 的 `still-image-time`，确认标识无冲突，再用 Apple `PHLivePhoto` 构建资源验证。还用故意错配的负例确认系统会拒绝错误组合。没有伪造标识或改写原文件来凑配对。

### 配对结果与缺伴范围

最终确定 3,727 对，生成 7,454 个独立、同基础名的副本，合计 24,679,779,005 字节。每对保留原文件名映射，配对副本逐文件 SHA 与恢复源一致；原恢复目录未改写。原恢复资源与配对副本两轮系统实况资源构建均通过。

纠正的 5 组同名误配按真实内部标识找到了跨名 MOV。另有 75 张照片缺少对应 MOV，其中 64 张为 HEIC、11 张为 JPEG；1 个带实况标识的 MOV 缺原照片，共 76 项缺伴。

为排查遗漏，额外扫描本路径 32,457 个图像及视频衍生文件和 21,786 个元数据文件，没有找到可确认的新伙伴。缩略图不能代替原尺寸照片，不带实况标识的普通照片也不能一律判成漏配。缺伴结论只针对当前已保存范围，其他手机、备份和尚未恢复路径仍可能有伙伴。

### 从容器检查推进到解码检查

4,258 个 HEIC 主图按原尺寸解码通过，辅助深度图和增益图未逐项独立解码。JPG、JPEG、PNG 完成已有图像解码；197 个 CR3 通过 ImageIO 默认图像解码，但这不能证明 RAW 传感器数据与嵌入预览均被独立完整核验。

3,954 个视频中，3,952 个的可见音视频轨通过默认 AVAssetReader 解码。两个例外保留了原失败记录并继续复核：

- 一个 MOV 默认或允许硬件的解码路径失败；关闭硬件后，软件解码完整通过 40 个压缩视频样本，音轨也通过。归类为解码路径相关兼容问题，根因未完全确定。另保存 NAS 既有 MP4 转码作备用播放，它不能替代原 MOV。
- 另一个 MOV 视频通过，但容器中音轨时长为零，仍有 73,644 个 48 kHz 单声道 16 位 PCM 采样。相关容器区与密文未加密部分字节一致，支持该字段不是本次解密写坏。按原采样表另提取 1.53425 秒 WAV，原 MOV 不改，音画同步仍未确认。

系统能够构建实况对象不保证所有播放器对每一条轨道都能正常播放。后续 12 对本地播放抽查通过，覆盖跨名配对与两个例外；这仍不等于 3,727 对全部完成用户实际照片库导入和播放验收。

## 11 从照片恢复转向 NAS 内分目录恢复

### 为什么改变存放位置

照片及配对结果保留在 Mac。之后清点的其他路径约 1.09 TB，而 Mac 当时剩余约 290 GiB，无法继续全量搬入。NAS 当时报告可用约 5.39 TB，因此按用户选择，改为在 NAS 上先归档原件，再逐目录恢复到 NAS 新树。

这不是把主密钥交给受灾 NAS。实际流程在 Mac 用单文件临时缓存解密，再通过加密通道写回 NAS 独立输出路径；主密钥始终留在 Mac。NAS 内归档属于操作回退副本，仍与受灾机共享硬件和管理风险，不能替代独立设备备份。[S08]

### 先补权限缺口再判断范围

管理员 root 会话补齐了 105 个受限位置，权限错误为 0。补采新增发现 178,438 个普通文件、20,763,592,563 字节，其中密文 32,663 个。与当时清点合并为 710,377 个普通文件、1,110,686,647,891 字节、415,121 个密文。

这些数字是当时已覆盖范围，后来 Docker 等边界继续扩大清点，不能引用为全 NAS 最终总数。发现的 1,637 条快照记录当时都属于 Docker，尚未建立用户共享目录存在完好快照的依据。

### 每个目录的实际恢复流程

1. 确认来源范围、子卷及挂载边界，排除救援输出目录和虚拟文件系统，不跟随符号链接。
2. 记录普通文件、目录、链接、硬链接信息及 ACL/xattr，计算源文件 SHA，保存源身份及变化检查记录。
3. 建立新原件归档，验证成员集合、类型、内容 SHA 和元数据，并与来源最终比对。
4. 对密文做记录与模式预检，再用代表样本验证端到端流程。
5. 从已验证归档取得单文件独立缓存，在 Mac 解密或原样复制，写到 NAS 全新目录。
6. 写入后立即重读 SHA，批次结束再全量重读，保存路径映射、格式检查及异常清单。

归档只有一个总 SHA 还不够：它能证明包文件未改变，不能证明成员无遗漏。文件名列表、成员数、文件类型、逐成员摘要及元数据都要核对。来源树发生变化时，不能用旧基线默默验收新状态。

首批回传通道曾在 TLS 握手阶段超时，记录表明尚未写入 NAS；随后改用 Mac 主动连接 NAS 的临时加密通道完成，未通过关闭防火墙解决。失败日志保留，成功回执另存。

### 首个共享目录的完成结果

该目录原件归档为 6,383,165,440 字节，含 1,394 个成员，其中 1,341 个普通文件、53 个目录。逐成员 SHA、GNU tar 内容及元数据比较、来源集合与身份稳定性均通过，Synology ACL 及其他扩展属性也有原始字节核验。

8 个代表样本通过后，全目录完成 1,288 份密文解密及 53 份原样复制，恢复大小 6,379,681,524 字节。输出总长与源普通文件总长的差额等于 `1,288 × 588`。即时及最终 NAS 读回 SHA 均通过，原密文未覆盖。

格式检查覆盖 260 个 JPEG/PNG、8 个 HEIC 主图、4 个视频及 197 个 CR3 默认图像；其余 819 份密文仅作密钥记录及输出完整性校验。本批格式失败为 0，但没有精确历史原件 SHA 对照，应用使用仍需相应验收。

## 12 六个小目录的冲突处理与结果

### 遇到同名版本先停止

首次小目录试运行发现 `.DS_Store.L0CK3D` 解密后会与后来新生成的 `.DS_Store` 同名，预检按不覆盖规则停止。已有原件归档通过验证，尚未生成恢复输出；它被保留，v2 使用全新批次目录继续，没有删除旧证据。

最终在六个目录中共记录 12 组冲突、24 个版本，包含 `.DS_Store` 与相应 Synology 资源文件。密文恢复版本和当前未加密版本分别保存，保留完整路径映射，没有任选一个覆盖另一个。路径处理还覆盖文件与目录冲突、救援保留目录名冲突及路径穿越拒绝。

## 13 全盘清点为何必须分开处理特殊数据

### 根目录与数据卷都要列账

已建立系统根目录 `/` 与数据卷 `/volume1` 的恢复清单，覆盖隐藏目录、根层散落文件、普通数据、应用数据、系统目录、链接和特殊边界。`/proc`、`/sys`、`/dev`、`/run` 等不作为普通业务数据递归归档。救援目录必须排除，避免归档套进自身。

后续扫描照片目录出现 91,123 个普通文件，共享目录出现 1,343 个，均比已验收基线多两个非加密文件。已完成批次仍按旧基线验收，新出现文件单独补账；没有把动态现场说成永久冻结的文件集合。

### 稀疏虚拟磁盘会改变容量估算

四个虚拟磁盘目录逻辑大小约 2.36 TB，文件 `st_blocks` 汇总约 300 GB。稀疏文件的未分配区域读起来是零，但不占相同的实际磁盘空间。普通解密器若逐字节写满逻辑尺寸，会把空洞实体化，恢复空间需求可能大幅增加。

归档需要明确保稀疏策略，恢复器也需要保稀疏输出与完整校验方案。`st_blocks` 之和还可能重复计算 Btrfs 共享块，不能直接当作独占物理占用。只有近期 `df` 或可用空间值，也不足以承诺所有特殊数据都能再放两份。

### Docker 子卷与数据库不能作为普通目录照搬

已发现 1,973 个 Docker 子卷边界。镜像层、快照、容器可写层及用户绑定目录需要分开，避免将共享内容全部展开后重复写入。数据库即使每个文件都解密成功，也可能缺少事务一致性；应在隔离的新环境做数据库恢复、结构检查和应用验收。

六个小目录工具仅允许固定来源，限制单文件 64 MiB、单目录 128 MiB。不能简单删去限制后用于数百 GB 数据。大目录还需断点续作、失败回执、容量控制、链接台账及顺序归档读取；反复从头解压 gzip 来随机取单文件会造成巨大开销。密文、照片和视频通常难以有效压缩，不应预设高压缩比。

### 当前后续目录顺序

优先处理 `homes`，再按重要性和容量安排 WebDisk、手机备份、媒体库等普通目录；Docker、数据库和稀疏虚拟磁盘另作专项批次。资料截点的记录仍显示后台清点未完成，**没有证据说明 homes 已归档或已解密**。

最近一次现场记录仍为 `libgld` 五线程暂停，NAS 持续供电。另一条既有自动跟进流程负责这项恢复工作；本文整理没有启动新的恢复作业、重新扫描 NAS 或更改监控。[S01、S08]

## 14 攻击入口调查与系统恢复边界

### 外部参考事件的漏洞判断不能直接移用

参考仓库作者最初猜测 GitLab RCE，后来依据其 DSM 登录日志与 RAM 中的登录插件环境注入残留，将入口高可信指向与 CVE-2024-10441 一致的技术链。其资料仍注明完整 HTTP 请求和执行链存在缺口。[S09]

本案目前没有同等完整的入口取证证据。不能把参考作者的日志时间、cron 文件、攻击链和 GitLab 恢复数量写成本案经历；也不能因样本相同直接认定从相同漏洞进入。

Synology-SA-24:20 公告列出 CVE-2024-10441 等相关漏洞及修复版本。其中 DSM 7.2.1 分支的门槛为 7.2.1-69057 Update 6；如果本案实际为该分支 Update 4，属于值得调查的未修补线索。该门槛只针对该公告，不代表 2026 年全部安全更新要求。[S10]

### 仍需调查的来源

保留并分析认证、DSM Web、nginx、系统日志、任务调度数据库、cron、服务及启动项，核对账号和管理员组、SSH 公钥、套件修改、容器配置、异常下载与出站记录。NAS、路由器和其他设备的日志应分别建立时间线，标明时钟偏差及重置造成的证据缺失。

扫描请求、登录失败、计划任务残留和日志中的删除命令各有证据范围。删除命令被记录不单独证明目标原先存在或删除成功；没有访问到完整请求也不能编造利用载荷。排查摄像头或路由器时需要它们自身的证据，不能仅按掉线时间归因。

### 可信系统恢复仍是后续工作

恢复数据与恢复系统信任是两个分别验收的任务。本文截点没有完成持久化清除、凭据审计或可信重建。建议在关键数据与证据妥善保全后，从可信介质和软件包建立受支持的系统环境，补齐更新，重新创建配置，再导入经验证的业务数据。

在干净设备上更换可能暴露的 NAS、SSH、同步、云服务和应用凭据，撤销旧会话及令牌，并重新核查外网映射、VPN 或访问网关。旧镜像层、脚本、插件和系统目录不能未经检查就覆盖回新环境。备份卷不要作为可写共享长期挂在受灾系统上。

重连生产网络前，分别验证数据可用、应用一致性、管理员与持久化配置、必要网络暴露和独立备份恢复能力。这里描述的是后续计划，没有把 NAS 当前状态标记为已清除感染。

## 15 他人复用时的步骤与停止条件

### 按证据推进的最短路线

1. 记录事件并隔离，核实设备是物理机还是虚拟机；不要直接套用 PVE 或其他内核的采集命令。
2. 确认加密活动及进程身份，停止已确认的继续加密，核对全部线程并尽早保全易失材料。
3. 封存采集、样本和密文，核对来源流、落盘读回、映射和缺页；失败材料也留档。
4. 在干净分析机确认样本及文件格式适配，提取候选，挑有精确原件的单文件测试。
5. 建立来源清单与副本逐路径 SHA，对权限、大小写、Unicode、链接和元数据缺口逐项补齐。
6. 代表样本通过后分批恢复到新树，记录每份输出，独立重读并做完整格式或应用验收。
7. 单列未恢复、缺伴、格式异常及历史原件缺失，完成独立备份，再按计划重建系统。

### 哪些情况需要停下当前批次

出现进程身份或启动时间变化、线程不再暂停、SSH 指纹异常、来源文件变化、归档或 SHA 不符、未知 footer 或模式、候选匹配失败、输出冲突、可用空间不足时，应停止依赖该条件的批次并保留日志。停止批次不等于删除失败产物、清空目录重跑或终止保全进程。

### 怎样写验收结论才准确

| 证据 | 可以说明 | 仍不能说明 |
|---|---|---|
| 来源与副本 SHA 相同 | 副本与已采集来源字节一致 | 来源本身未受破坏 |
| 归档成员集合与 SHA 通过 | 此归档覆盖并保存指定来源 | 归档是独立异地备份 |
| key record 检查通过 | 候选与该记录存在结构匹配 | 文件全文正确或无重复加密 |
| 输出读回 SHA 一致 | 输出落盘后与本次生成记录一致 | 与感染前原件一致 |
| 完整格式解码通过 | 被检查的内容可由该解码路径读取 | 所有附加内容均通过或等于原件 |
| 精确历史原件 SHA 相同 | 对应文件逐字节与该原件一致 | 其他文件也全部正确 |
| 应用恢复及操作通过 | 通过的操作在该环境可用 | 所有业务功能与生产容量均已验收 |

### 每批建议保存的记录

为每一批保存来源范围、时间和时区、工具版本及摘要、来源文件清单、归档成员清单、输入输出路径映射、SHA、失败及未决项。秘密材料放在单独受控目录，交接只引用文件位置与验证状态，不复制密钥内容。

保留密文原件、内存原件、独立分析副本和恢复结果，分别记录保管位置。当前 Mac 的原密文与恢复目录同机，NAS 的原件归档也在同机，它们都有用途，但尚未构成独立第二设备备份。后续应补一份独立介质或另一设备的完整副本，并以读回 SHA 及实际恢复演练验收。

## 16 常见报错与本案解释

| 现象或报错 | 本案定位 | 合理的下一步 |
|---|---|---|
| `Cannot allocate memory`，直连口无相应包 | Mac 本地路由或发包路径异常 | 同期抓包并核对接口、源地址及路由作用域 |
| `subsystem request failed` | NAS 未提供 SFTP 子系统 | 在路径可信的前提下评估 `scp -O`，传完独立验收 |
| `Permission denied` 后 rsync EOF | SSH 认证尚未成功 | 核对实际账号及认证层，避免连续重试触发限制 |
| maps 或 exe 权限拒绝 | 普通账号无权读取 root 进程信息 | 在已有授权的终端交互提权，记录结果 |
| `address_offset_overflow` | 极高虚拟地址的读取偏移限制 | 记录缺页范围，改进错误处理；不伪造页面 |
| `errno_5` 或 EIO | 特殊映射通过进程内存接口不可读 | 核对映射，保留缺页，不认为 sudo 必然解决 |
| `PARTIAL_HOLES` 且摘要通过 | 保存传输一致，但有页面未采得 | 检查候选依赖是否跨洞，保持部分采集标识 |
| 预期 EOF marker 不匹配 | 本案会话标记与原工具不同 | 先验传输和完整布局，再按证据配置 profile |
| 同名 HEIC/MOV 无法组成实况 | 文件名不能证明同一资产 | 检查内部标识及 still-image-time，不强配 |
| JSON 语法失败但输出 SHA 一致 | 文件保存一致，格式仍有例外 | 保留未改文件，找精确原件或进行应用调查 |

S02 项目中的《导出沟通内容》《初步调查与处置顺序》《Mac隔离直连NAS步骤》；用于最初症状、旧 IP 失败、Synology Assistant 搜索及直连地址发现过程。

S03 项目中的《再次独立采集步骤》、`process-stream-23393-v2`、`offline-key-23393-v2` 与 `offline-decrypt-23393` 的说明及相关脚本；用于采集失败、缺页处理、候选提取和严格单文件工具的约束。早期说明中“尚未执行”是当时状态，后续是否执行以实际记录为准。

S04 《救援电脑交接摘要.md》及相关对话；用于跨电脑摘要交接、手机热点联网方案和仍待救援 Mac 现场核验的网络隔离条件。此前双接口路由、抓包、临时主机路由撤销及最终连通性过程以 S01、S02 的历史记录为准。

S05 本案《恢复完成报告》及 `recover_verified_photos.py`；用于照片基线、复制差异、批量输出、现场 marker 和验证分级。

S06 本案《遗漏复核报告》；用于 91,121 个来源文件覆盖、63,667 个输出复核、27 个链接目标及精确原件由 3 份增至 4 份的修正。

S07 本案《处理结果与例外》及实况配对、媒体解码和播放抽查记录；用于 3,727 对配对、76 项缺伴和两个媒体例外。

S08 本案《首批NAS归档恢复结果》《小目录恢复结果》《根目录待恢复清单》《NAS内逐目录恢复计划》和 `CONTINUE.md`；用于权限补采、归档恢复、重名保全、JSON 例外及当前待办。

上述资料来自同一项目及其引用的本地工作记录；分享版只提取必要结论，不附真实照片、原始内存、密钥、账号或完整私人路径。

### 项目工具的定位

`process-stream-23393-v2` 是本事件进程流采集适配；`offline-key-23393-v2` 读取已保存映射并提取特定样本布局的候选；`offline-decrypt-23393` 为严格单文件副本工具。`photo-audit-20261030` 保存复制盘点、配对、格式验证和归档恢复代码，其中多处是本案固定路径、固定 profile 或固定来源范围。

这些脚本需要重新审阅、参数化和兼容性验证才能用于其他设备。本文整理没有运行恢复器、连接受灾 NAS 或读取真实候选密钥与内存字节；它交付的是案例与排障参考，后续进展应以新的批次回执追加更新。
