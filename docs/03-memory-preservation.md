## 05 核实加密进程并保留易失证据

### 核实 PID 与全部线程

本案进程名为 `libgld`，PID 23393，`/proc/23393/exe` 指向 `/usr/bin/libgld (deleted)`，有 5 个线程，线程号分别为 23393、23395、23396、23397、23398。后续多次记录均显示它们为 `T (stopped)`，`TracerPid` 为 `0`。[S01、S03]

`(deleted)` 表示原可执行文件的目录项已删除，运行进程仍可能保有映射和内核引用。它不能解释为“病毒已经清除”。此时 `/proc/PID/exe`、进程映射和内存仍可能提供重要证据，先结束进程会失去这条机会。

在 NAS SSH 窗口使用只读检查，其他设备必须替换 PID：

```sh
date -u
uptime
grep -E '^(Name|State|Pid|PPid|TracerPid|Threads):' /proc/23393/status
sudo readlink /proc/23393/exe
for f in /proc/23393/task/*/status; do
  grep -E '^(Pid|State|TracerPid):' "$f"
done
```

普通账号读 root 进程的链接失败，可能是权限限制。先记录退出码及报错，必要时在该终端交互执行 `sudo -v` 或 `sudo -i`，由设备所有者输入密码。临时凭据缓存不等于永久免密，也未必在另一个 SSH 会话生效。

### 暂停与终止的差别

在确认某进程正在加密且已完成 PID、启动时间和样本身份核验后，停止信号可以阻止其继续执行，同时保留地址空间。其他新事件中可由响应人员对**已核实的目标**使用 `sudo kill -STOP PID`，随后检查全部线程，不能只按名字批量操作。本案进程已经暂停，记录阶段不再发送 STOP，更不发送 CONT 或 KILL。

若信号后仍为 `D` 状态，不能宣称加密已停止；应观察全部线程、CPU 时间及 I/O 变化并继续调查。进程状态、开始时间与可执行摘要需要一起记录，避免 PID 重用导致采错对象。


## 06 物理 DSM 内存采集的过程与缺页分析

### 为什么没有照搬 PVE 整机内存方案

外部参考事件从 PVE 来宾 RAM 找到恢复材料。本案是物理裸机，没有对应的可信宿主内存接口。磁盘快照也不包含进程内存。本案改为读取已暂停进程的可读映射，经 SSH 二进制流写到 Mac；没有在 NAS 上先生成数 GiB 的 dump 文件。[S03、S09]

采集前记录 CPU 架构、内核、Python、进程启动标识、线程状态及样本摘要，并检查接收盘容量。进程映射约 6.08 GiB。采集工具与 stderr 日志分流，保存发送端字节数、流 SHA、SSH 退出状态、接收端落盘读回结果及每个映射的收据。

### v1 采集失败和 v2 的修正

用户报告救援 Mac 约有 580 GB 可用空间后，采集前检查确认 NAS Python 3.8.15、x86_64、约 6.08 GiB 可读映射，`/proc/PID/mem` 接口可打开，5 个线程处于暂停状态。此前准备的 v1 工具在沟通 Mac 通过 13 项合成测试。一次密码输入错误由用户明确说明是自己输错，之后的检查成功；这不是采集失败原因。

第一次实际采集的 v1 在第 15/19 个映射附近发生 `OverflowError`，日志记录已写出 6,529,812,480 字节、来源状态 `FAILED`、SSH 退出码为 1。失败的 `.tar.part` 及日志保留，没有重命名成完整证据或删除；v2 的重试入口先对救援 Mac 上这段失败流做来源收据读回校验，再开始独立采集。

本地测试复现了 `os.pread` 处理极高地址时的偏移溢出。v1 只捕获 `OSError`，导致该异常提前结束采集。v2 增加溢出处理、逐页重试、缺页地址及原因记录，继续采集后续区域；修正后的 v2 通过 20 项本地测试。这修复了**遇错中止和记录不足**，没有使原本不可读的页变得可读。第一次 v2 采集完成后，用户考虑到现场数据难以再现，要求再保留一份独立采集；确认启动器每次创建新目录后执行，没有覆盖旧证据。第二份 v2 的记录目录为 独立的新建采集目录（私人目录名省略）。

两份 v2 独立采集均处理了 19 个映射，来源流、接收端读回和映射文件摘要检查通过，但均为 `PARTIAL_HOLES`。它们分别封存，未将两次活系统采集拼接成一份“完整内存”。重复采集增加了独立证据副本，但没有补回相同缺页；后续因此停止继续重采，改为在救援 Mac 上离线检查副本。

### 相同的 12 KiB 缺页是什么

| 映射 | 缺失长度 | 读取结果及解释 |
|---|---:|---|
| `[vsyscall]` | 4,096 字节 | 高地址 `0xffffffffff600000`，`os.pread` 偏移无法表示，记为 `address_offset_overflow` |
| `[vvar]` | 8,192 字节 | `/proc/PID/mem` 读取返回 EIO，记为 `errno_5`；属于内核提供的特殊映射 |
| 合计 | 12,288 字节 | 采集状态仍为部分缺页，不能把零占位当作实际内容 |

最初仅有错误类别，后续通过提权只读查看映射表，才将这两处对应到 `[vsyscall]` 和 `[vvar]`。因此最终解释依据后续核验，不能假装首次失败时就已查明所有原因。

增加 sudo 权限能解决读取 maps 的权限问题，不能修复高地址表示限制，也不能保证内核允许读取特殊页。两次都缺同样位置，重复运行相同工具没有补回这些页面。

### 为什么仍然可以继续验证恢复材料

离线提取器检查候选所需的代码、模式字节、指针和 48 字节材料是否与缺页重叠；有重叠就拒绝。此次候选取自已校验且不跨已记录空洞的区域。后来真实密文与精确原件的验证表明，这些材料足以恢复已验证文件。该结果不改变“采集不完整”这个事实。

三个结论应分开：传输摘要一致说明收到的字节一致；映射摘要一致说明保存的映射与收据一致；恢复成功需要另外的文件验证。即便工具显示 `COMPLETE`，也只代表选定的可读映射没有报告空洞，不包括全部地址空间、寄存器、内核 RAM 或已释放页。

没有为追求完整而在受灾 DSM 上盲装 AVML、加载 LiME 或不匹配的内核模块。已审阅上游记录没有提供本物理 DSM 的实机验收依据；工具兼容性和现场崩溃风险必须另行评估。
